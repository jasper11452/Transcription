# 现代化意图（INTENT.md）

本文件由 `/code-modernization:modernize` 记录，后续命令（`brief`、`reimagine` 等）读取此文件，
不再重复询问。**不要用推测覆盖这里写下的目标栈。**

## 目标

**reimagine —— 按新架构从零重建。**

用「理解优先」的路径做重建：先从现有代码里提取真正的意图与业务规则，再用一套新架构重新搭建，
而不是把旧目录改名。

## 从 / 到

- **从**：Python 3.12 单进程 FastAPI + MLX 本机模型 + React 18/Vite/Tailwind 3 前端，
  源码 6.5k 行 Python（`src/` + `tests/`）、3.6k 行 TS/TSX（`frontend/`）。
- **到**：**模块化单体**。仍是一个进程、仍绑 `127.0.0.1`、仍让 MLX 模型在 lifespan 里常驻，
  但把转录流水线、引擎注册表、存储、Web 层划成边界清楚的模块包；
  引擎注册表升级成真正的「接口 + 适配器」；分片状态机显式化。

  选择理由（用户确认）：保住「单进程常驻模型」这个本机优势，风险最低。

## 必须守住

- **顺手修已知 bug。** 迁移过程中发现的问题一并修掉，改动需要更仔细的验证。
  → 意味着 `extract-rules` 阶段要把「旧代码实际行为」和「应该的行为」分开记录，
  `review` 阶段由人来确认哪些是 bug、哪些是刻意保留的怪癖。

用户没有选择「旧系统迁移期间继续跑」——本工具是本机单人工具，旧版就是当前系统本身，
不存在并行线上的生产流量。

## 用户原话

> 你想对这个代码做什么？ → **按新架构从零重建**
> 过程中必须守住什么？ → **顺手修已知 bug**
> 重建后它该是什么样子？ → **模块化单体（推荐）**
> 现代化的工作区放哪里？ → **就在本仓库（推荐）**

## 工作区约定

- 快照（只读）：`legacy/transcript/`
- 分析产物：`analysis/transcript/`
- 重建产物：`modernized/transcript-reimagined/`
- 三者均已写入 `.gitignore`，不污染产品仓库的历史。

## 范围边界（沿用 PRODUCT.md，重建时不要扩大）

**非目标即承诺**：实时听写、批量/文件夹排队、翻译、说话人分离、字幕编辑器、云端/多用户、鉴权。
重建不是加功能的机会。
